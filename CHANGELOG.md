# Events&I – changelog

## 2026-10-30

- [x] **Set-up check on the admin page** — A panel at the top, shown only when something needs putting right: `DEV_MODE` on a live site, missing or short `TOKEN_SECRET`, no Resend key, a missing or test Turnstile secret, `SITE_URL` not set, not https or on another host, settings still at their example values, migrations not applied (from wrangler's `d1_migrations`), and the cron Worker: never run, not run for 20 minutes, or with a `TOKEN_SECRET` (compared by a fingerprint), `SITE_URL`, `EMAIL_FROM` or Resend key unlike the site's. The cron records each run in a new `status` table (migration 0010); a database without it does not stop the cron. e2e covers the cron findings; checked in jsdom with axe.
- [x] **Starter site and CI** — `examples/starter/` is a minimal Astro site with the booking form, check-your-email, confirm, manage, 404 and privacy-notice pages (the notice a template to adapt, covering what Events&I stores, who sees it, Cloudflare and Resend, and retention). `scripts/starter-e2e.sh` runs the end-to-end test on a throwaway copy of it around the working tree, so contributors need no site of their own, and a GitHub Actions workflow runs the unit tests and it on every pull request. Without a 404 page Pages answers unknown addresses with the home page, which the starter's 404 page avoids.
- [x] **Security hardening for the public beta** — From an independent security audit (no blockers). Unconfirmed registrations hold at most a quarter of the in-person places (at least 5); beyond that a registration holds nothing and gets a place on confirming if one is free then, so made-up sign-ups can no longer fill an event for 48 hours (a waitlisted registrant who confirms when a place is free, with nobody confirmed waiting, now gets it too). The organiser's "half way to expiry" warnings come as one email per event per cron run. A confirmed address gets at most three reminders a day from the form. The admin page requires `ADMIN_EMAILS` outside local development, refuses to be framed and sends no referrer. Access refusals now say what to check (`ACCESS_AUD`, `ACCESS_TEAM_DOMAIN`, an application not covering the address), and the team domain may be pasted with `https://`. Inbound replies try at most five references; request bodies are refused by declared size before being read; event pages with a backslash are refused (and ignored by `/events/next`). e2e covers each.
- [x] **Plain HTML components, review fixes** — `html/sent-to.html` for the check-your-email page; props with defaults take them from the component and the rest use capitalised placeholders (the contact link too), escaped; Turnstile's loader is taken from the component; the CSS scoping stops the build on anything it does not handle (at-rules, selector lists in brackets, `html`/`body`) rather than producing wrong CSS; one plain `<style>` and a `<script>` are required; paths with spaces work. The id test also covers ids looked up through the event-wording lists. README: escaping, script paths, how to keep a page's own wording, and that it looks a little different without Starlight.
- [x] **Sending: a 409 is never taken as sent** — A retry whose idempotency key Resend has seen with a different body (a joining-instructions copy whose poll line changed, say) marks those people "uncertain": not sent again, not counted, and shown on the admin page; so is a piece left pending longer than Resend keeps keys (resuming a day-old failure cannot send twice). A 409 for a request still in flight is retried. Calendar updates keep their key from the planned calendar, so a conflict there does mean the same update went. A message piece always uses one key form, whether one email or many. The dev outbox compares bodies as Resend does and gains a `crash-after-send` address (accepted, then cut off); e2e checks no second copy after a crash and "uncertain" when the retry differs. Cancelled messages count only people who had a copy, and a session cannot be deleted while a message still to be sent (or failed) is addressed to it.
- [x] **Sending in pieces, third review** — Pieces carrying joining instructions are now 3 people (30 with `PAID_PLAN`), down from 5. A retried piece keeps the idempotency key and the plain/instructions split it was recorded with, even if someone in it has cancelled or been promoted since. Pieces shrunk to find a refused address return to full size once it is set aside, so the rest of a big message is not sent one per run. A refusal for everyone tried (two people refused before anyone has had it: a wrong sender, say) marks the message failed with its error instead of setting the whole audience aside and calling it sent. Writing and recording a piece is a constant number of SQL statements (via `json_each`), whatever its size. e2e covers the refusal for everyone.
- [x] **Sending in pieces, second review** — Each piece is recorded as pending before it is sent and retried as exactly that piece, with links and calendar stamps fixed at the message's start, so a retry is the same email under the same idempotency key; a 409 for a request still in flight is retried later. Attempts are counted when a piece is claimed (so a run killed outright counts), a failed message can be resumed from the admin page, and an address Resend refuses shrinks the pieces until that one person is set aside, so everyone else still gets it. Queued calendar updates claim each person before sending, with day-fixed links and a key from the planned calendar. Counts are of distinct people; a message carrying older joining instructions no longer marks anyone as behind. The cron runs a message piece, then a couple of calendar updates beside it (more without one). The dev outbox simulates a refusal (`fail-send`) and an outage (`fail-500`); e2e covers both and the resume.
- [x] **Review fixes for sending in pieces** — A message's audience is fixed when it starts (recipient ids stored), and its joining instructions are the version chosen when it was written. Only the run holding a claim (with a token) can finish a piece, so a cancel in between stands. A repeated idempotency key that Resend answers with 409 counts as sent, and a single email keeps one key whichever endpoint it goes to, so a retry can neither wedge a message nor send a copy twice. A message whose pieces fail five times running is marked failed; the cron serves messages falling due first and those failing least, so one bad message cannot hold up the rest, and alternates with queued calendar updates. Holds and retention run before any sending. A first piece that fails leaves the message sending (with its error on the admin page) instead of an error that invites sending it again. Calendar updates are all queued before the first few go, and a failed one is retried a few times. "Promote all" sends host lists once, after the last few. `PAID_PLAN=true` sends bigger pieces. The dev outbox now refuses a "fail-send" address and honours idempotency keys, and e2e covers a refused piece, a message falling due meanwhile, and giving up.
- [x] **Sending to a whole event in pieces** — No request now goes over the Workers free plan's 50 queries or 50 outbound requests. Messages send a piece at a time (100 plain copies, or 5 carrying joining instructions), record each delivery as it goes, carry a Resend idempotency key per piece, and are finished by the cron Worker from their delivery records; a failed piece is retried without sending anyone a copy twice, and a part-sent message can be cancelled. A session change sends the first 8 calendar updates and queues the rest for the cron (migration 0009). "Promote all who fit" works two at a time, the admin page repeating it. e2e: 12 people, queued updates, a message over three runs, a cancelled one.
- [x] **Repo-scan fixes (part 1)** — "Promote all who fit" sends each host one list, not one per person promoted. A multi-day event's `day` calendar key stays on the day it was first sent for, and the week-ahead reminder stays on that entry, so adding an earlier day sends only the new day; e2e checks adding a day and folding one into another. An event ending before 6am the next day (a late dinner) is still one day in emails. Retention also deletes messages (their bodies can name attendees) and removes the author's address from joining instructions. The README lists the two automatic emails it missed ("registration deleted" and the waiting-list confirmation).
- [x] **Events over several days** — In-person attendees get one calendar entry per day with something on it (the first keeps the key `day`, so one-day events are unchanged) instead of one entry spanning the nights, each with that day's schedule; the week-ahead reminder only before the first. The confirm and joining-instructions emails give the dates as a range ("Saturday 7 to Sunday 8 November 2026"). e2e with a weekend event made through the set-up API; `tests/dates.test.mjs`.
- [x] **events.andeye.com: this release's features** — Three more feature cards (polls with a "count me out" line, set-up on the admin page, any time zone; nine in the three-column grid) and the plain HTML components in "What you need". Site builds.
- [x] **Review fixes for event set-up** — An event with registrations can no longer have its end moved into the past (the 30-day retention would have deleted everyone at the next cron run), nor end more than a day before its last session; registration must close before the end. Clones keep each time's wall clock in the event's zone across a change to or from summer time, need a page of their own, rewrite session ids only on an `id-` prefix and refuse id collisions, and copy only the organisers' own poll options. Sessions cannot be deleted once a host has been sent a list or a scheduled message is addressed to them, and the delete re-checks bookings itself. Time zones are stored as the runtime names them, and offsets such as `+01:00` refused; a new zone keeps the event at the same moment. The admin page works without the events API on a site not yet given its wrapper (named in the README's upgrade note).
- [x] **Plain HTML components** — Each Astro component's script now lives in its own module (`astro/rsvp-form.ts`, `confirm-panel.ts`, `manage-panel.ts`), and `scripts/build-html.mjs` generates plain HTML versions in `html/` from the components' markup (placeholders for the props), a stylesheet with every rule scoped under the fragments' `.eai` wrapper, and the bundled scripts (build output, not committed). `tests/components.test.mjs` fails if `html/` is out of date or a script looks up an id the markup lacks. The confirm page no longer assumes remote attendees join "the talks".
- [x] **Review fixes: time zones and host lists** — VTIMEZONEs are built once per zone and day with one formatter per zone (about 116 ms per calendar file before, now a few ms for 200), searched a day at a time on whole minutes. The admin page converts a wall time with the offset at the instant itself (a second pass), so times near a change of offset in zones far from UTC are no longer an hour out; a time in the skipped hour moves forward. Lowering an event's host-list gap sends lists held back under it; host lists are claimed before sending, so a request and the cron cannot send the same one twice; a failed note to a replaced host no longer stops the others. The admin page on a new installation shows just the form to create the first event.
- [x] **Event set-up on the admin page** — A new Events section switches between events, edits the current one (title, venue, page, dates, time zone, extra question, the form's wording), creates a new event and clones the current one to a new start (sessions moved by the same amount without hosts or online links, the latest joining instructions as version 1, polls with their active options; never registrations, answers or suggestions). Sessions can be added (core, tour or opt-in, with a capacity) and deleted while nobody has booked them and, for core sessions, before any invitations have gone out. `src/setup.ts`, `/api/admin/events`; nothing emails anyone (e2e checks the outbox).
- [x] **Attendance wording from the event** — Migration 0008 adds `in_person_label`, `remote_label` and `tour_legend` to events; the booking form and manage page use them (component props still override), so the two pages always agree without props. The status line for remote attendees no longer assumes the event is talks ("You are registered to join remotely."). The example seed carries AMYBO's wording.
- [x] **Optional gap between host lists** — A per-event setting (migration 0007, admin Settings, default 0 = every change as before): a host who had a list less than that many minutes ago waits, and the cron Worker sends one list gathering every change once the gap has passed; within a day of the session changes go at once. e2e checks a held change, the gathered list and validation.
- [x] **Admin page and forms in the event's own time zone** — Date and time inputs, their labels and displayed times on the admin page follow the event's `timezone` ("UK time" for Europe/London, otherwise e.g. "New York time"); the booking form's closing time and opt-in session times and the manage page's session times do too. Checked in jsdom for an America/New_York event (inputs show and post the right instants) and in e2e.
- [x] **Messages to just the opt-in sessions** — The compose filter gains "Signed up for" (an opt-in session such as the dinner; people waiting for it only with the waiting-list box ticked) and two attendance choices that split "In person": "In person for the day" and "Only coming to opt-in sessions". "In person" itself still reaches both. e2e checks the counts.
- [x] **Review fixes for the booking-form polls and DMARC** — Poll totals count only confirmed registrations, so booking-form rankings from made-up addresses never sway them; a ranking made out of date while the form was open (poll closed, option gone) is dropped instead of blocking the registration, and only malformed answers are refused. Replies are refused only on DMARC `fail` or `permerror` (`none`, a domain without a policy, is common for small organisations), and an organiser's out-of-office is dropped before that check, so it never bounces. After a move only the ranking list is rebuilt, so its status region stays in place and screen readers announce the move. README notes that the form and its API must share a host for the Turnstile check.
- [x] **Calendar files in any time zone** — Events outside Europe/London were written in UTC; now every known IANA zone gets local times with a TZID and a VTIMEZONE built from the runtime's Intl data (each change of offset within a year of the event found by search and written as its own observance, so half-hour zones, zones without summer time and the southern hemisphere all work). Europe/London keeps its rule-based block; an unknown zone still falls back to UTC. Tests in `tests/ics.test.mjs`.
- [x] **Replaced hosts are asked to delete their lists** — When a session's host changes or is removed on the admin page, a previous host who was sent a list gets one short email asking them to delete it (never on a dry run, and not when the same host is saved again). README's list of automatic emails updated. The open question of whether "Save without emailing anyone" should also hold back host emails is in TODO.md.
- [x] **Polls on the booking form** — The booking form shows each open poll (optional) with the same ranking list as the manage page, now one shared module (`astro/ranking.ts`). Only a list the person has rearranged is sent, so nobody is counted in by default; rankings are checked before the registration is saved and stored with it. No suggestions there, as the address is not confirmed yet. e2e checks, plus a jsdom and axe run of both forms (0 violations); `astro check` clean.
- [x] **Polls: an invitation in the joining instructions, and DMARC on replies** — Joining instructions (and the reminder sent to anyone who registers again) end with "Have your say: …" for each open poll the person has not answered, with the manage button relabelled; no new email kind, and the admin page says so. Replies to suggestion emails are refused at SMTP time when Cloudflare's topmost `Authentication-Results` header records a DMARC result other than pass; headers further down (the sender's own) are ignored, and a missing header refuses nothing, as it has been reported missing on Worker delivery.
- [x] **Turnstile: action and hostname** — The booking form's widget now has `data-action="eventsandeye-register"`, and the server refuses a token unless siteverify reports that action and the host the registration was posted to, so a token solved on another site or form sharing the widget key no longer passes. Unit tests in `tests/turnstile.test.mjs` (siteverify stubbed).
- [x] **Markdown renderer nits** — Code spans are held aside like links, so nothing in them becomes emphasis; italics need the `*` to hug words and not sit inside a word or number (`2*3*4` stays as typed); link URLs may contain balanced brackets (Wikipedia-style). Three new tests in `tests/markdown.test.mjs`.
- [x] **Polls with a "count me out" line, registrant suggestions and email-reply moderation** — Registrants rank a poll's options on their manage page (most wanted first) and move a line under the ones they would join; the admin page tallies who would join, who would stay at home, first choices and a preference score, with names. Registrants can suggest their own option and rank it at once; the organiser is emailed and replies `yes`, `no` or `use <wording>` (Cloudflare Email Routing → the cron Worker's new `email()` handler, accepted only from an organiser address with a reference signed by `TOKEN_SECRET`), or decides on the admin page; wording that matches an existing option merges the suggestion and keeps everyone's ranking. Migration 0006, `src/polls.ts`, `src/inbound.ts`, new e2e checks and `tests/inbound.test.mjs`. The sent log gains poll totals (no names). Automatic replies (out-of-office) are dropped without a reply or bounce; only a whole-line answer counts; only the headers are read until sender and reference check out, and HTML is read in linear time. Polls are deleted with the 30-day retention. An independent review's findings (From-header display-name spoofing, parallel suggestions beating the caps, ballot races with merges) are fixed, with unit tests in `tests/polls.test.mjs`. Nothing emails registrants; ballots are deleted with the registration.
